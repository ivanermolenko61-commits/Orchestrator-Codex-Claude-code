# /agentq — перекрёстные роли: Codex пишет фронтенд, Claude пишет бэкенд, код ревьюит другой сервис

Скрипт: `bash ~/.claude/skills/agentq/codex-review.sh <команда>` (дальше — `CR`); движок `agentq_global.py` рядом, состояние задачи — `<корень репо>/.ai/` (исключено из git локально), поэтому работа переживает закрытие чата и VS Code. Протокол и роли — в этом файле и в README репозитория Orchestrator-Codex-Claude-code (источник установки).

Задача: $ARGUMENTS

## Роли (одинаково во всех рабочих проектах)
| Часть | Автор | Независимый reviewer |
|---|---|---|
| Фронтенд, клиентские тесты | Codex (`gpt-6.1-sol`, без инструментов, ответ — JSON) и его исправления | Claude (opus, отдельный процесс без инструментов и сессии) |
| Бэкенд, серверные тесты | Claude Code (сам тимлид или один coder-субагент) и его исправления | Codex (read-only, пустой каталог, только текст) |
| Защищённые зоны, миграции, CI, права, платежи, сам agentq | Claude Code | Codex |
| Постановка, контракт, распределение, интеграция, итоговый отчёт | Claude Code (тимлид) | — |

Недоступность одного сервиса — блокер маршрута. Автоматической подмены автора или reviewer другим сервисом нет, «Claude пишет всё» молча не включается. Gemini/OpenCode в эту схему не входят.

## Ограничение циклов и достаточность качества

Применять общее правило «Завершение задач без лишнего усложнения» (в личном профиле владельца, если он подключён; иначе действуют пункты ниже). Оно уточняет постановку, оценку замечаний и выбор проверок; не отменяет независимый PASS, проверки точного SHA, разделение ролей и действующие бюджеты.

- Перед реализацией зафиксировать проверяемые требования текущей задачи и критерий остановки. Не добавлять новые критерии готовности в каждом раунде без связи с исходным требованием или конкретным существенным риском.
- В первом ревью просить собрать все обнаруженные существенные замечания одним отчётом. Не дробить известные замечания на последовательные раунды. Это не обещание найти все дефекты с первого раза.
- Для каждого BLOCKER/MAJOR требовать: нарушенное требование или риск, условия возникновения, место и причинную связь в коде либо воспроизведение, последствия. Необоснованную метку разбирать с reviewer, а не автоматически усложнять код. Скрытый риск безопасности может быть существенным и без падения теста.
- Исправлять подтверждённые блокеры одним согласованным пакетом. Стиль, предпочтения архитектуры и улучшения вне задачи — отдельно, если не нарушают требования и не создают существенный риск.
- После исправлений проверять закрытие замечаний и регрессии изменённого поведения; расширять анализ только по затронутым зависимостям или новым свидетельствам. Обязательный независимый reviewer получает полный актуальный diff и контекст: область повторной проверки не служит запретом замечать новый существенный дефект.
- Каждый повторный полный прогон или модельный вызов должен иметь конкретное основание. Успешные свидетельства переиспользовать только при сохранении значимых входных данных и требований к SHA; правила движка не обходить.
- Два последовательных круга без приближения к готовности или повтор одного дефекта — повод для диагностики причины и упрощения подхода вместо автоматического третьего круга прежней тактики. Продолжать необходимые исправления и приёмку в пределах уже разрешённого бюджета; при исчерпании сохранить кандидат, подтверждённый блокер и предложить конкретный путь. Не повышать лимиты и не объявлять готовность искусственно.
- Доработка координатора в задаче продукта допустима только как явно выделенная необходимость при доказанном блокере и отсутствии существующего разрешённого маршрута. Не начинать её молча, не создавать новые механизмы проверки ради необязательных пожеланий.
- После выполнения критериев и обязательной приёмки выполнить все уже разрешённые этапы передачи/выпуска и закончить. Не запускать новое ревью принятого неизменённого кандидата «для уверенности».

## Шаг 0. Какой маршрут (всегда первым, без вызовов моделей)
`CR route` →
- **10** — у проекта свой координатор (`scripts/agentq.py` с `review`/`rereview`): действуй по `.claude/commands/agentq-codegen.md` и `docs/agentq.md` проекта. `CR start/cycle/review` не запускать — второй цикл поверх первого запрещён (движок сам откажет).
- **12** — координатор есть, но без перекрёстных маршрутов: назови недостающее, остановись, реши с Иваном. Не переходи ни к `CR`, ни к «Claude пишет всё».
- **11** — глобальный маршрут не готов (нет/не вошёл Codex или Claude, нет общих правил зон): покажи список `MISSING:` и остановись.
- **0** — глобальный маршрут готов. `NOTE:` показывай Ивану (нет карточки проекта → создать по шаблону и показать зоны и роли; нет `checks` + `check_image` в `.agents/agentq.json`, закоммиченных ДО задачи → приёмка невозможна без явного `CR waive`; Docker и образ нужны локально, движок их не собирает и не скачивает).
- `MODE=учебный` — учебный режим сохраняется: сначала краткий план и «да» Ивана, потом `start --plan-approved`; код целиком не пиши, предложи часть, которую Иван напишет сам.

## Шаг 1. Постановка (тимлид)
1. Не указана задача — `CR status`: есть активная — продолжай с шага, где остановилась; нет — спроси. Не git — скажи и остановись. Текущая ветка `main`/`master` — создай `aq/<коротко>`.
2. Раздели задачу на части по таблице ролей. Файлы клиента (`frontend/`, `client/`, `web/`, `ui/`, `*.tsx|jsx|vue|svelte|css|html`) — Codex, серверные (`backend/`, `server/`, `api/`, `*.py`) — Claude; если угадать нельзя — `.agents/agentq.json` (`frontend`/`backend` маски, `checks`). Файлы защищённых зон — только `protected` (тимлид, ревью Codex).
3. **Смешанная задача:** сначала общий контракт (поля, типы, ошибки, права, загрузка, поведение при сбое) в файл ≤4000 символов; `CR start "<цель>" --kind mixed --contract-file F`; затем `CR unit <uid> --kind backend|frontend|protected --files …` (до 8 файлов, исключительное владение: пересечение отказано), `--after <uid>` — frontend стартует после принятого backend, если зависит от него. Изменение контракта — только с согласием обеих сторон и новым ревью затронутых единиц.
4. Чисто серверная задача: `CR start "<цель>"` (единица `main`, backend). Чисто клиентская: `start --kind mixed` + контракт (хотя бы краткий) + frontend-единица.
5. Параллельная работа допустима только при согласованном контракте и непересекающихся файлах; интеграция последовательная. Вложенного делегирования нет, если оно не предусмотрено в задании.

## Шаг 2. Бэкенд и защищённые зоны (автор Claude → reviewer Codex)
Реализуй сам (или одним coder с точным контрактом и списком файлов) прямо в ветке задачи `aq/…`: отдельная рабочая копия и `integrate` нужны только автору Codex, чужого кода тут нет. Защита та же: ревью привязано к точному SHA коммита, `finish` не засчитает единицу, если после PASS её файлы менялись (включая секретные и lock-пути, скрытые от модели), ветка сменилась или в них есть незакоммиченные правки; коммит, затрагивающий пути, которые модели не показываются, на ревью не уходит. Чужие незакоммиченные правки вне файлов задачи в ревью и приёмку не входят и не коммитятся (`git add <файлы>`). Работа последовательная: параллельный `CR` в том же репозитории получает BUSY. Прогони тесты проекта, закоммить локально только файлы задачи → `CR review [uid] <effort>` (`low` простая правка, `medium` обычно, `high` данные/авторизация/оплата/миграции). Коды: `0 PASS`, `1 FIX` — исправь BLOCKER и MAJOR (спорное замечание не исправляй молча, укажи в итоге), коммит, снова `review`; `2` блокер (сбой/таймаут/нет VERDICT — вызов израсходован, автоповтора нет, назови причину); `3 LIMIT` — остановись и опиши разногласие; `4 BUSY`. Движок не пустит клиентский код в backend-единицу (`РОЛЬ:`) — оформи frontend-единицу.

## Шаг 3. Фронтенд (автор Codex → reviewer Claude)
`CR cycle <uid> <effort>` делает всё сам: Codex пишет полное содержимое файлов → доверенный код проверяет путь, зоны, размер, скрытые символы, секреты, новые `eval/innerHTML`, усечение, удаление тестов → коммит в отдельной рабочей копии `agent-worktrees/<проект>-aq-<id>-<uid>` (ветка `agent/codex/…`) → (движок сам гонит `checks` точного SHA в контейнере без сети и секретов — см. «Механические проверки» — и только при зелёных зовёт reviewer; красные возвращаются автору) → Claude-reviewer в отдельном процессе → FIX/UNCERTAIN возвращаются Codex-автору с дословным отчётом → повтор до PASS или остановки по прогрессу. Вручную ничего между сервисами не переносится. После `PASS` и зелёных проверок — `CR integrate <uid>` (ff-only в ветку задачи, push нет; без проверок на точном SHA или обоснования `waive` отказ); если ветка ушла вперёд после закрепления базы — нужен новый base и ревью, автоматического rebase нет.

## Как разбирать остановку по лимиту

- Различать три причины: контрольная точка или остановка по прогрессу внутри задачи, явный предел Ивана (`--max-calls`), квота подписки сервиса или отказ CLI. По сообщению LIMIT не объявлять исчерпанной подписку.
- Если Иван просит решение проблемы повторных остановок, не ограничиваться очередным промптом «запроси ещё вызов»: показать, закрыты ли конкретные BLOCKER/MAJOR и починены ли проверки (прогресс), и дать готовое поручение с критериями завершения (`CR rethink` с более простым подходом либо решение Ивана).
- Различать предложение изменить пределы, разрешение пользователя на это, реализацию в коде и установленную версию. Предложение само по себе не разрешает обходить явный предел Ивана. Новые полномочия не приписывать пользователю.
- При смягчении любого числового предела сохранять прекращение зацикливания (два круга без прогресса), фиксированные требования, учёт расхода и независимую приёмку; увеличение числа вызовов само по себе не решает причину повторных FIX.

## Область бюджета: конкретная задача плана
- Различать уровни: **проект** (журнал `.ai/ledger.json` — история для аудита), **конкретная задача плана** (цепочка работы: `start` и все её `--continues`; только здесь считаются бюджет и контрольные точки), **попытка** (отдельный `start`/id внутри цепочки).
- Одна задача плана — один `start`. Несколько самостоятельных задач плана не объединять единицами одной задачи agentq: единицы делят цепочку (12 вызовов, предел Ивана), и принятые единицы уменьшали бы бюджет следующей. Единицы — части одной задачи (backend + frontend, модули одного результата).
- Внутри незавершённой задачи складываются вызовы автора, исправления и ревью всех её единиц и попыток.
- После выполнения критериев и обязательной приёмки (`ACCEPTANCE: VERIFIED…`, запись PASS) следующая задача плана начинается обычным `start` и расходует с нуля. Расход, receipts, вердикты закрытой задачи остаются в журнале для аудита и не вычитаются из следующей; продления «из-за истории закрытых задач» не запрашивать.
- Незавершённая задача расход не теряет: новый чат (состояние в `.ai/`), другой id или формулировка, `finish --abandon`, повторный запуск, в том числе после того как Иван запустил другую самостоятельную задачу (`--new-work`), — возвращаться только через `start --continues <id>`. `--new-work` — решение Ивана о другой работе, а не способ получить чистый счёт для той же.
- Общий бюджет нескольких задач действует только при явном указании Ивана такого охвата. `--max-calls N` относится к одной цепочке и в другие задачи не переходит. Своего общего предела на проект или несколько задач тимлид не вводит.

## Бюджеты, прогресс и восстановление
- **Контрольные точки, не запрет**: 3 вызова автора, 3 ревью на единицу и 12 вызовов на цепочку работы (`--continues` включает уже сделанные). До точки вызовы идут сами. После неё следующий вызов разрешён только при подтверждённом прогрессе последнего круга: закрыты конкретные BLOCKER/MAJOR прежнего отчёта (reviewer помечает `[ЗАКРЫТО]`/`[ОСТАЛОСЬ]`/`[НОВОЕ]`) или исправлены падавшие проверки. Косметика, переформулировка замечания и расширение требований прогрессом не считаются; прогресс оценивается по закрытым проблемам, а не по их числу, отдельной модели для оценки нет. Резерв сохраняется ДО вызова и не возвращается; лимит времени можно только сокращать (`AQ_TIMEOUT`). Расход, receipts, вердикты и история кругов никогда не сбрасываются.
- **Два круга без прогресса** подряд: автоматическая передача автору и новые ревью останавливаются (код 3, «СТОП»), управление у тимлида. Тимлид разбирает причину, проверяет трактовку требований и записывает более простой подход: `CR rethink <uid> "<причина и подход>"` — он идёт в запросы автору и reviewer, круг разрешается. Один пересмотр на единицу (и на всю цепочку): повторное зацикливание — окончательная остановка с блокером, выполненной работой, незакрытыми замечаниями и рекомендацией; решает Иван (принять остаток, сузить требования или `finish --abandon` и `start --new-work`). Явно заданный Иваном предел (`start --max-calls N`) жёсткий: прогресс его не продлевает, продолжение его не поднимает, значение пишется в журнал. Без `--max-calls` жёсткого предела нет — только контрольные точки.
- **Продолжение (`--continues`)**: расход, история прогресса, пересмотр подхода и последний отчёт ревью принадлежат единице с тем же uid. Не поддерживаются и отказываются понятной ошибкой до создания единицы: переименование, объединение прежних единиц, пересечение файлов прежней работы под новым uid, смена семейства ролей (frontend ↔ backend/protected); внутри семейства (protected → backend) тот же uid продолжает работу. Reviewer видит все изменения продолжаемой работы с её исходной базы (frontend: база автора остаётся текущей, исходная хранится для ревью) вместе с прежним отчётом; потерянный отчёт при бывших ревью — остановка до вызова. Принятые файлы других единиц прежней работы исключаются из области единицы без файлов и после начала продолжения без своей единицы не меняются. Журнал `.ai/ledger.json` проверяется на согласованность перед стартом и перед каждым платным вызовом; повреждение — остановка без обнуления. Локальное состояние доверенное: намеренная правка владельцем компьютера не обнаруживается.
- Приёмка: статическое ревью — промежуточное свидетельство. `CR integrate` и успешный `CR finish` требуют (1) независимый PASS на точном SHA, (2) успешные механические проверки того же SHA (или зафиксированное `waive`), (3) неизменность проверенных файлов и ветки. PASS без проверок → `finish` возвращает 1, пишет «НЕ ПОДТВЕРЖДЕНА», состояние сохраняется (`CR checks <uid>` выполняет проверки без вызова модели). Непринятая задача (в том числе частично) никогда не закрывается сама: только явным `CR finish --abandon` (расход остаётся в журнале, дальше `start` требует `--continues`/`--new-work`). Новый неотслеживаемый файл в принятых путях единицы после PASS отменяет приёмку. Итог: `ACCEPTANCE: VERIFIED` или `VERIFIED-WAIVED` (журнал `acceptance`).

## Механические проверки (изоляция, доверенный источник)
- Конфиг — `.agents/agentq.json` **на базовом коммите задачи** (`git show base:…`): `{"checks": {"backend": [["ruff","check","."],["python","-m","pytest","-q","-p","no:cacheprovider"]], "frontend": [[…]]}, "check_image": "локальный-образ:тег" | {"backend":…,"frontend":…}, "check_timeout": 600}`. Рабочее дерево и кандидат конфиг не подменяют; коммиты задачи с правкой этого файла отклоняются. Конфиг нужно закоммитить ДО `start`.
- Исполнение: `docker run` без сети, без секретов (только HOME, CI), `--read-only`, `--cap-drop ALL`, `no-new-privileges`, лимиты pid/памяти/CPU, пользователь 65534, исходники — точный коммит (`read-tree`+`checkout-index`, без .git, export-ignore и ссылок) монтируются read-only и копируются в tmpfs; образ берётся из локальных (`--pull never`, закрепляется по ID). Код возврата и вывод читает хост; результат (SHA, образ, команды, коды) пишет хост в `.ai/`, кандидат до него не дотягивается.
- База: красная команда перезапускается на базе. Красная только у кандидата → регрессия, возврат автору. Красная и на базе → `ok=None` (уже существующее падение): не вина кандидата, но и не подтверждение — нужна починка базы отдельной задачей или решение Ивана.
- Нехватка окружения (нет Docker/образа/проверок) — блокер ДО платного вызова с причиной; состояние сохраняется. Для неприменимых проверок: `CR waive <uid> "<причина ≥20 символов>"` — разрешено только если `checks` для этой роли в доверенной конфигурации нет; причина идёт reviewer-у, в отчёт и журнал. «Не требуется» без причины и обход настроенных проверок невозможны.
- Остаточный риск: код кандидата в контейнере может сам завершиться с кодом 0 или подделать вывод тестового раннера — проверки это свидетельство для ревью diff, не доказательство; защита — независимое ревью diff, неизменность конфига/образа и запрет удаления тестов.
- Ответ привязан к точному запросу (receipt). После сбоя `CR cycle`/`review` снова: готовый ответ читается без нового вызова; без ответа — блокер, повтор запрещён. Новый id, новая цель или новый коммит для обхода учёта не работают: после непринятой задачи `start` требует явного решения — `--continues <id>` (израсходованное и история прогресса переносятся) или `--new-work "<причина ≥20 символов>"` (только по решению Ивана; причина пишется в журнал `.ai/ledger.json`).
- Codex: только `gpt-6.1-sol`, effort минимально достаточный (`low` простое, `medium` обычно, `high` с причиной), без авто-повышения и fallback. Claude-reviewer — подписочный вход, без API-ключей, MCP и hooks.
- Результат проверок — только то, что запустил доверенный код на точном SHA в контейнере; текст агента «тесты прошли» доказательством не считается. Свидетельства (запросы, ответы, отчёты) лежат в `.ai/task/calls/`.

## Итог
`CR finish` и отчёт Ивану: что сделано, кто автор и reviewer по каждой единице, SHA, проверки (запущены ли вообще), вердикты и раунды, блокеры, ветки. Не «PASS по тимлиду» и не саморевью как независимая приёмка.

## Запрещено
- `git push`, деплой, миграции прод-БД — только по явной команде пользователя.
- Запускать Codex с инструментами, менять параметры его запуска, подменять модель; писать клиентский код вместо Codex; повторять вызов после неопределённого исхода; запускать второй цикл ревью поверх проектного координатора; править файлы, закреплённые за автором, в основном дереве.
- Если reviewer изменил код — это авторские правки, их проверяет другой сервис (reviewer прав на правки не имеет).

## Как писать промпт под /agentq (для ассистента в чате)
Если ответ заканчивается планом дальнейших действий для исполнителя, готовый копируемый промпт давать сразу в том же ответе, без отдельной просьбы Ивана и без «могу подготовить промпт». Включать цель, критерии готовности, ограничения, ожидаемый итог и уже данные полномочия; не подменять готовое поручение одним обсуждением плана.

Перед каждым готовым промптом явно указывать, куда его отправить: **Claude Code** или **Codex**, и при необходимости проект/чат. Не оставлять выбор исполнителя пользователю по догадке.

Перед каждым промптом для Claude Code выбрать формат и написать его одной строкой над блоком: «Формат: обычная задача» или «Формат: /agentq — <почему>».

- **/agentq** — задача меняет код в git-репозитории и ей полезно независимое ревью diff: данные, миграции, авторизация, оплата, общая логика; или пользователь сам попросил. Не для задач без diff: ревьюер смотрит только коммиты задачи.
- **Обычная задача** — эксплуатация и проверки без нового кода: сборка/перезапуск контейнеров, команды на сервере, уборка, чтение и сверка, документы, Notion.
- Смешанная задача — описать кодовую и эксплуатационную части отдельными этапами одного поручения до конечного результата; для кода использовать соответствующий маршрут ревью. Не заставлять Ивана переносить отдельное поручение после каждого технического шага.

Формат блока `/agentq`:
- **Обязательно включать команду в сам копируемый промпт:** если выбран формат `/agentq`, первая строка внутри блока должна быть `/agentq <цель задачи>`. Подпись «Формат: /agentq» над блоком не заменяет команду. Это относится и к ответам на отчёты, поручениям исправить замечания и продолжениям: для продолжения активной задачи — `/agentq` без аргументов. Перед выдачей проверять наличие команды внутри блока; не перекладывать её добавление на пользователя.
- первая строка — `/agentq <цель одной фразой>`, дальше тем же сообщением: «Готово когда», ограничения (защищённые файлы, чужие незакоммиченные правки не трогать), желаемый `effort` ревью, если важен (`high` для миграций/данных/оплаты), что прислать в итоге;
- не дублировать то, что навык делает сам: маршрут, ветка `aq/…`, `CR start`, локальный коммит, цикл ревью, `CR finish`;
- push, слияние, деплой и миграции прод-БД включать в полномочия исполнителя только при явном разрешении пользователя на соответствующее действие; уже данное разрешение сохранять в поручении, повторно не запрашивать;
- продолжение прерванной задачи — просто `/agentq` без аргументов.

## Поручение до выпуска и установки

При просьбе «довести до конца», «закрыть вопрос», «выпустить», «установить рабочую версию»:
- Сразу формулировать одно поручение на весь результат: исправления → целевые проверки → независимая приёмка → разрешённая публикация и слияние → установка → проверка установленной версии и команда использования. Отдельно перечислять действия, на которые уже получено разрешение. Если финальное действие ещё не разрешено, сначала подготовить конкретный проверенный кандидат для единственного согласования.
- До работы закреплять контракт версии, критерии готовности, бюджет вызовов этой конкретной задачи плана с резервом на исправления и условия остановки (расход закрытых задач в него не входит, см. «Область бюджета»). Не подставлять одноразовые числа из прошлого выпуска и не увеличивать бюджет без разрешения.
- В пределах полученных полномочий и бюджета самостоятельно выполнять исправления, проверки и необходимые повторные ревью. Не заканчивать каждый шаг просьбой разрешить следующий, если он уже входит в поручение. Не сбрасывать историю, receipts и счётчики.
- Сохранять выбранную цель до результата или оговорённого блокера. Не переключать Ивана между «выпустить инструмент» и «вернуться к приложению» по собственной инициативе; следовать согласованному условию переключения.
- Проверять замечания по контракту и последствиям: отличать подмену проверяемого кода или ложный успех от безопасной остановки, диагностики и пожеланий вне версии. Метка MAJOR требует обоснования; спор разбирать явно, не скрывать находку и не требовать PASS заранее.
- Проверять итоговый SHA и затронутые зависимости. Не повторять неизменённые проверки и ревью без конкретного основания. При приёмке самого движка использовать независимую процедуру вне проверяемого механизма.
- После принятия кандидата выполнять все разрешённые этапы выпуска без дополнительного поручения. Различать локальный коммит, опубликованную ветку, main и установленную версию; готовность подтверждать установленными файлами и подходящей проверкой запуска.
- Завершать одним итогом: рабочая установленная версия, SHA, приёмка, расход и команда использования; либо конкретный подтверждённый блокер и сохранённый результат при исчерпании оговорённых возможностей. Не обещать отсутствие будущих ошибок и не выдавать исправление за независимый PASS.

Это правило постановки и сопровождения работы. Оно не является свидетельством, что какой-либо конкретный выпуск уже принят или установлен.
